# Эквайринг Точка-Банка для 42master.ru

Интеграция использует **платёжные ссылки интернет-эквайринга** API Точки.
Это оплата комиссии предпринимателем платформе, а не перевод с банковского счёта клиента.
Месячный расчёт и состав счёта сохраняются в ЛК; оплату этого счёта обслуживает банк.

## Песочница по умолчанию

В настройках окружения:

```dotenv
TOCHKA_ENVIRONMENT=sandbox
TOCHKA_LIVE_ENABLED=False
```

Код сам выбирает публичные тестовые данные из документации банка:
`https://enter.tochka.com/sandbox/v2`, токен `sandbox.jwt.token`,
customerCode `1234567ab`, merchantId `200000000001097`.
**Рабочие ключи для песочницы не нужны.** Реальный JWT в sandbox не отправляется.

Официальное ограничение: песочница отдаёт статические ответы правильной структуры,
но **не открывает платёжную форму, не проводит оплату и не списывает деньги**.
Её ответ APPROVED также не переводит счёт в «Оплачен». Нет локальной кнопки
демонстрационной оплаты. В ЛК показан режим песочницы, идентификатор операции
и результат серверного запроса.

Источники:
- [Песочница](https://developers.tochka.com/docs/tochka-api/pesochnica)
- [Сценарий интернет-эквайринга](https://developers.tochka.com/docs/tochka-api/internet-acquiring-integration)
- [Платёжные ссылки](https://developers.tochka.com/docs/tochka-api/opisanie-metodov/platyozhnye-ssylki)

## Запуск

```bash
python manage.py migrate --noinput
python manage.py process_monthly_billing
# Либо существующий постоянный процесс:
python manage.py run_business_scheduler --interval 60
```

После расчёта появляется долговечная очередь `AcquiringPayment`. Процесс формирует ссылки,
проверяет статусы старых операций и повторяет подготовку новых счетов. Ошибка банка не
удаляет локальный счёт. На странице счёта есть POST-кнопка формирования/проверки.
GET страницы и браузерный возврат не считаются доказательством оплаты.

Используются:
- `POST /acquiring/v1.0/payments` — ссылка без автоматического чека;
- `POST /acquiring/v1.0/payments_with_receipt` — ссылка с фискализацией;
- `GET /acquiring/v1.0/payments/{operationId}` — серверная сверка.

Базовые адреса выбираются фиксированно по среде. Переадресации API не разрешены,
TLS проверяется. При необходимости доверенного CA задайте путь `TOCHKA_CA_BUNDLE`;
проверку сертификата отключать нельзя. Proxy используется из окружения.

## Где получить рабочие ключи

1. В интернет-банке Точки: **Сервисы → Все сервисы → Интеграции и API → Создать JWT-ключ**.
2. Задайте название, срок действия и разрешения `MakeAcquiringOperation`,
   `ReadAcquiringData`, `ReadCustomerData`; подтвердите создание кодом из SMS.
3. Сохраните JWT в защищённых переменных окружения сервера. Не записывайте его в Git
   и не присылайте в чат. JWT не обновляется refresh-токеном: по окончании срока
   его перевыпускают в интернет-банке.
4. `customerCode` вашей компании получите через **Get Customers List**, у объекта
   `customerType: Business`. Это компания-получатель комиссии, не компания плательщика.
5. `merchantId` получите через **Get Retailers** для этого customerCode. Торговая
   точка должна быть активна, иметь статус `REG` и поддерживать `sbp`/`card`.

Для этой интеграции собственной компании достаточно JWT: OAuth client_secret не нужен.
`client_id` сохраните при выпуске, если впоследствии будете подключать вебхуки.
Сейчас используются серверные проверки API, поэтому вебхуки не требуются и
неподписанные входящие события об оплате вообще не принимаются.

Официальные инструкции:
- [Выпуск JWT](https://developers.tochka.com/docs/tochka-api/algoritm-raboty-s-jwt-tokenom)
- [Идентификаторы](https://developers.tochka.com/docs/tochka-api/terminologiya)
- [Get Retailers](https://developers.tochka.com/docs/tochka-api/api/get-retailers-acquiring-v-1-0-retailers-get)

## Переход в продуктовую среду

```dotenv
TOCHKA_ENVIRONMENT=live
TOCHKA_LIVE_ENABLED=True
TOCHKA_JWT_TOKEN=<секретный JWT>
TOCHKA_CUSTOMER_CODE=<код вашей компании>
TOCHKA_MERCHANT_ID=<ваша торговая точка>
SITE_URL=https://42master.ru
# Выберите способ формирования чеков явно:
TOCHKA_RECEIPT_MODE=bank
TOCHKA_TAX_SYSTEM=<ваша система налогообложения>
TOCHKA_VAT_TYPE=<ваша ставка НДС>
```

`TOCHKA_RECEIPT_MODE=bank` требует подключённой фискализации в Точке; передаются
позиции комиссий, email предпринимателя, налоговая система и НДС. Например,
значения системы из API: `osn`, `usn_income`, `usn_income_outcome`, `esn`, `patent`.
Налоговую систему и ставку указывает владелец — код не выбирает их за него.
Если фискализация обеспечивается отдельно, можно явно выбрать `TOCHKA_RECEIPT_MODE=none`.
В режиме live отсутствие этого выбора блокирует создание ссылки до настройки.
Обычная ссылка `/payments` сама по себе не формирует кассовый чек.

После изменения переменных перезапустите веб-процесс и планировщик. Старые sandbox-
операции сохраняются отдельно и не могут оплатить live-счёт. Для pending-счетов
будут созданы live-попытки. Уже оплаченные исторические счета не выставляются повторно.
Полный переход/оплату проверяют в продуктовой среде: песочница этого не умеет.

## Защита оплаты и спорные случаи

Оплата подтверждается только ответом GET банка со статусом `APPROVED` и совпадением
operationId, paymentLinkId, customerCode, merchantId и суммы. `AUTHORIZED`,
`WAIT_FULL_PAYMENT`, редирект и query-параметры браузера не подтверждают оплату.
Повторная проверка сохраняет дату оплаты и не дублирует уведомление колокольчика.

Каждой попытке соответствует UUID paymentLinkId (уникальный номер заказа банка).
Перед POST её состояние фиксируется в БД. Если ответ потерян/процесс прерван,
новый заказ вслепую не создаётся. После ручного поиска операции в Точке по
paymentLinkId получите operationId и выполните:

```bash
python manage.py recover_tochka_payment <UUID-попытки> <operationId>
```

Команда сначала проверит соответствие операции через API и откажется привязать
чужой заказ или неправильную сумму. Ошибки 400/401/403/404/429 можно повторить с
тем же paymentLinkId после устранения причины; неопределённые ответы/таймауты
требуют сверки. В логах и интерфейсе не сохраняются токены и полные ответы банка.

При изменении суммы/аннулировании счёта текущая ссылка в ЛК выбирается по новой
сумме. Ранее выданную банком ссылку нельзя считать отменённой: интеграция не
выдумывает отсутствующий метод отмены. Её операции продолжают проверяться;
оплата старой суммы, второго заказа или аннулированного счёта не закрывает новый
счёт и помечается `payment_review_required`, с уведомлением в ЛК. Возвраты и
частичные возвраты также требуют сверки; деньги автоматически не возвращаются.
TTL новых ссылок — 1440 минут. Истёкшая по ответу банка операция допускает новую ссылку.

В Django admin доступны записи AcquiringPayment, безопасные коды ошибок и
флаг сверки счёта. Платёжные данные карты не запрашиваются сайтом и не хранятся.

## Проверка в этой среде

Проверяются тестами формирование запросов, суммы, фискализация, привязка операции,
невозможность оплаты по редиректу/fixture песочницы, идемпотентность и восстановление
после таймаута. Прямой запрос из текущего облачного окружения к sandbox завершился
URLError (соединение не установлено). Успешный живой вызов банка здесь не подтверждён;
на сервере нужен сетевой доступ к enter.tochka.com и корректная цепочка TLS.
